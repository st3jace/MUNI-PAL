## Reading the honesty column

- `not_applicable` is never a judgment call. It is either a set-intersection (S08), a Literal (S16), or a named rule (S11, S17, S15 hold).
- `unknown` always carries a non-empty reason and is counted separately in `counts`.
- A checklist item whose required path a knob dropped (LAB03: `S08.item_P2.2`, `S08.item_P3.3`) is a conformance row like any other: `pass` when BFMS reports the mechanical expectation (`covered 0/n`), `fail` when it does not. It is never `not_applicable` (the set-intersection runs over the scenario family, not the materialised pack) and never `unknown` (BFMS was called and answered). The knob effect lives in the ratcheted reason (`absent by scenario knob`), which the e2e test asserts per scenario.
- The only `fail` rows expected in a green run are the two F9 sub-assertions in S05 and the F16 sub-assertion in S12 (`known_gaps_accepted` in the report; `report.KNOWN_GAP_KEYS`).
- The S13 `filed_never_applied` row is derived from the event log: the CDA document may read `filed` iff a CDA filing event fired; none is carried, so `signed` is the expected end state.
